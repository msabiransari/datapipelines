# scripts/sample-data-lake/requirements-pyiceberg.txt — the pinned Python
# environment for the ONE stage DuckDB cannot do: writing the Iceberg table.
#
# Installed into .tools/pyiceberg-<version>/ by lib/iceberg-venv.sh; never into the
# system Python, and never into the app — this is a build tool, exactly like the
# pinned DuckDB CLI, and nothing at runtime imports it.
#
# EVERY line is an exact ==, including the transitive tree: this file IS the lock.
# It was produced by resolving `pyiceberg[sql-sqlite,pyarrow]==0.12.0` with
# `pip install --dry-run --report` on 2026-09-07 (Python 3.14.6, macOS arm64) and
# writing back every package the report named.
#
# WHY THERE ARE NO --hash LINES, stated rather than skipped. A `--require-hashes`
# file must carry the hash of the wheel pip actually selects, and that selection is
# per platform AND per Python minor: the 28 wheels resolved above are cp314/macOS
# arm64, and the same 28 VERSIONS install from entirely different files on
# linux-amd64 or Python 3.11. Pinning this machine's hashes would make the build
# refuse to run anywhere else, which is worse than the exposure it closes. What
# holds the line instead: the versions are exact (a compromised NEW release cannot
# enter), and the artifact this environment produces is checksummed object by object
# in manifest.json and re-derived from those objects by verify.sh — so a tampered
# writer changes the published bytes and the manifest says so.
#
# Regenerate with:
#   python3 -m venv /tmp/rq && /tmp/rq/bin/pip install --dry-run \
#     --report /tmp/r.json "pyiceberg[sql-sqlite,pyarrow]==<new version>"
# and update `param pyiceberg_version` in sources.lock in the same commit.
