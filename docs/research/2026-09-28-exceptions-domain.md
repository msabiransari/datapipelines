## Most consequential findings

1. **PostgreSQL streaming DQL commit failure disappears on the successful path.** `modules/dag/src/main/kotlin/co/datapipelines/executor/NodeRunner.kt:848` unconditionally calls `runCatching { conn.commit() }` in `datasourceQuery`'s finally and discards its result. `SourceStreaming.enable` at :1156 disables autoCommit only for PostgreSQL with nonzero fetch size and originally enabled autoCommit. The node's normal result is returned even if commit fails. The comment at :837 explicitly allows author DQL to contain multiple statements with side effects, so the rationale that a fully consumed cursor makes commit failure harmless is not sufficient for all permitted SQL. Caller path: `runOnResolvedDatasource` -> datasource DQL query -> `NodeRunner.run` -> `PipelineExecutor.completeNode`; the normal result can proceed to completion while durability is unknown. On a previously failed node, preserving the original exception is appropriate, but the commit failure should remain secondary evidence. Source review warrants a targeted reproduction with commit acknowledgement loss and side-effectful author SQL before deciding semantics.

2. **Selector close/cancel paths lose cleanup failures.** `modules/datasources/src/main/kotlin/co/datapipelines/datasources/ReadOnlyStatementLease.kt:93,98,182,189,190,193`. Setup failures preserve the primary failure but discard statement/connection close errors (:93/:98). `LeasedStatement.close` sets its state CLOSED then discards statement and connection close results (:189/:190); repeated close does not retry this normal-close branch. `abandon` discards cancel failure (:182), then invokes pool discard; a late worker closes its statement (:193), again silently. Caller is `modules/parameters/.../SelectorRunner.kt:285` (`statement.use`), and the selector worker can therefore return its row result without cleanup evidence. The connection may remain physically live if its driver refuses close. Production Hikari discard at `pooling/ConnectionPoolManager.kt:146` logs eviction failure, but only exception class, and reports no structured failure to `abandon`; the generic interface's :59 close is fully silent. This is separate from the intentional policy that a cleanup failure must not replace a primary selector error.

3. **Current outer catalog errors become a less-specific namespace.** `modules/datasources/src/main/kotlin/co/datapipelines/datasources/CurrentNamespace.kt:67` catches every Throwable via runCatching and returns no outer segment. This differs from the same file's :78/:82 precise classification of unsupported inner-schema reads, connection failures and other errors. `SchemaIntrospector.effectiveNamespace` (:309) and `TableStatsReader` (:69) consume the result as a usable effective namespace when nonempty. Inference: a multi-catalog driver fault can silently remove catalog qualification; whether a particular driver then yields ambiguity, wrong metadata or a later refusal needs a failing-driver test.

4. **Live heartbeat persistence failure is only DEBUG-visible.** `modules/dag/.../ExecutionProgress.kt:141` and :149 log heartbeat/progress errors at DEBUG and continue. `PipelineExecutor.heartbeat` (:946) repeatedly invokes the former. `StaleExecutionSweeper` (:62–65) and `ExecutionRepository.sweepStaleRunning` (:544) treat old heartbeat timestamps as instance loss. Inference: sustained write failure on an active executor while another instance can still sweep may classify live work ABORTED. The broader persistence policy is intentional, but export alone cannot reveal DEBUG messages at a higher configured threshold; this path needs an observable failure counter or appropriate event level.

5. **Transform rollback omits secondary cleanup evidence.** `modules/dag/.../TransformNodeRuns.kt:1056` ignores DROP failure for each already-written table. It is invoked by catch blocks :200/:203 while rethrowing the primary transform error/cancellation. The pipeline fails, so this is not false success; residual tables are left to final staging teardown. The distinct staging partial-table path (`H2StagingSql.kt:160` -> `H2Staging.rollbackAfterFailure` :254) does log and preserve the reservation when cleanup fails, providing an existing stronger pattern.

6. **Optional SQLite statistics fallback is broader than its stated reason.** `modules/datasources/.../TableStatsReader.kt:158` turns every SQLException for an optional row-estimate query into an empty result. `TableStatsPlans.kt:219` makes SQLite's sqlite_stat1 optional because it can be absent before ANALYZE. `readPlan` at :89–93 turns that empty result into `rowEstimate=null`, `statsSource=none`. Permission, corruption, cancellation or connectivity failures at that query are also treated as no stats, although later index queries may independently fail. Narrow refusal classification and fallback diagnostics should be evaluated.

7. **Invalid per-case clock pin is treated as missing.** `modules/templates/.../TransformTestRunner.kt:81` parses `input.now` with runCatching/getOrNull; `runCase` :157 uses `caseNow(input) ?: now`. The supplied invalid pin therefore becomes the caller's clock, or no clock pin (clock builtins then refuse). This is production template test/probe execution code despite the class name. It should be distinguished from intentionally accepting either offset or local timestamp grammars.

## Logged degradation and intentionally handled outcomes

Cancellation flag reads (:58) return null after WARN and continue execution; a failing Redis read may delay cross-instance cancellation until later polls or deadlines. Cancellation key deletion (:67) logs and relies on TTL. `CancellationRegistry.kt:420,432` keeps trying other statements when a driver refuses cancellation/close, but records only DEBUG message text. Cancellation cannot be made reliable merely by shipping logs.

Lake view initialization can intentionally serve surviving views (`LakeInstanceInitializer.kt:111,113`) and records outcomes. A failed outcome write (:151, and `DefaultDatasourceRegistry.kt:220`) is WARN-only. Resource-owner close failures are generally tracked more carefully: `TrackedDuplicate.kt:144` records exhausted handles, and `LakeInstanceOwner.kt:278` stores `ownerCloseFailure` and logs failure rather than asserting the owner closed. In contrast owner bootstrap close (:345) drops its secondary failure. `LakeInstanceDataSource.kt:56` locally discards its duplicate close error, but the tracked duplicate registry can log/recover the residual separately; do not claim no system-level observation exists there.

The H2 staging pool preserves original exceptions via `addSuppressed`, counts refused physical closes and logs reset/replacement/sweep failures. `H2ConnectionPool.kt:470` logs replacement failure and marks the pool LOST if no holder remains. These are deliberate containment paths, not silent success.

`ScheduledRunWorker.kt:161` is not swallowing: it logs the full throwable and writes UNKNOWN/start_failed to the ledger, blocking future work until reconciled. Scheduler pause failure (`SchedulerAdmission.kt:66`) logs while the admission gate is already closed. Likewise validators/parsers return explicit rejection objects, domain wrappers are thrown, and async SelectorPool failures are handed to its deferred result; adding duplicate logs at every such catch would obscure the boundary.

## Diagnostic policy observations

Many operational catches retain only `exception.message` or class, not the throwable, SQLState or structured outcome. Conversely raw JDBC messages may contain author data or credentials: `typesystem/H2RestrictedSession.kt:168` deliberately replaces a password-bearing driver exception with SQLState/vendor code and no cause. An audit must not mechanically attach raw exceptions everywhere. Sanitized context, a stable event/error code, execution/trace identifiers, cause type and suppressed-cleanup details belong at a defined boundary.

Kotlin runCatching catches Throwable, including cancellation and VM Errors. Several sites describe their intent as handling a parse refusal or nonfatal driver exception while using that broader construct. Audit expected failure families explicitly; do not make all exceptions disappear merely to guarantee continuation. The swallowed result/cause is distinct from whether control flow correctly communicates failure to the caller.
