## Method (re-runnable)

1. **Use-case inventory** — every screen in `docs/ui-screens.md` (§4.1–§4.20, §5, §6) plus
   `dashboards.md`, `scheduler.md`, the pipeline-editor spec's user-facing sections, and the
   versioning lifecycle table. Each screen: its verbs, the role each verb is rendered for,
   and its stated behavioural contracts (toasts, dialogs, states, keyboard, responsive).
2. **Coverage inventory** — every file in `tests/browser-tests` read; per class, the concrete
   scenarios it asserts and the role it logs in as.
3. **Claim verification** — the original audit used grep plus test reads. The source review
   found false negatives in G2/H8; those entries now distinguish existing assertions from
   remaining work. Before dispatch, map each proposed scenario to the existing test method
   and assertion, or record the search scope and terms for an absent scenario. A class name
   alone is not a coverage witness.

**Proxy limits:** an empty grep proves only that the searched spellings were absent. A test
may name the flow differently or touch it incidentally. Conversely, opening a page does not
assert its use cases. The remaining gap claims are review inputs, not an exhaustive proof
that all release behavior has been inventoried.

Reproduce the source inventory from the repository root (the class count is a source proxy,
not JUnit's executed-test count; inspect the matching files as well as the totals):

## P0 — release-blocking gaps in browser journey coverage

A release where one of these is broken can ship a dead core flow. These are proposed
browser-coverage gaps; some have lower-layer guards or partial browser coverage, identified
below. The existing fixtures support the local journeys; each lane must verify its setup.

### A. Session boundary

- **A1. Log out** — avatar menu → Log out: session cookie cleared, rail gone,
  `/dashboard` now redirects to login, and browser Back does not resurrect the session.
  Zero suite files mention logout (verified). Spec §3.4.
- **A2. Session expiry mid-use → `HX-Redirect`** — invalidate the session (expired JWT),
  then click a rail link (a boosted request): the response must land the browser on
  `/login?expired=true` with the expired banner — never a login form swapped inside
  `#app-main` (the §5.1 single bridge; §6). This is the #202/#207 bug family; no test.
  Buildable: seed a user, mint the session, tamper/expiry via config override or DB, click.
- **A3. Deactivated mid-life** — deactivate the signed-in user (admin UI from a second
  session, or DB), next navigation → `/login?error=inactive` with cookie cleared
  (§4.1, auth §11A.3). Pairs with the admin deactivation verb (H1).
- **A4. Login error variants** — `locked` banner (lock the account, attempt login);
  `inactive` (deactivated local user attempts login). `credentials` is covered;
  these two are not. Rate-limit lockout is config-dependent — see NOT-list.

### B. Admin users (§4.12) — the onboarding path

- **B1. Create local user → one-time password → first login.** Super admin creates a user
  (email + display name + workspace + role), the one-time password renders in the
  persistent `#admin-notice` panel (shown once, survives the toast), that user signs in and
  hits the forced-change gate. The gate is covered from a *seeded* user
  (`LoginGoldenPathBrowserTest`); the admin *creation* path — panel, `must_change_password`,
  role assignment — is not. Verified: `UiBoundaryShotsBrowserTest` renders the table only;
  no suite file clicks an admin verb.
- **B2. The remaining row verbs** — Reset PW (new one-time password + lockout cleared),
  Unlock, Disable local (hash cleared → OIDC-only note), Activate/Deactivate (toast names
  email; deactivation copy states the ~60s JWT/keys window), Reset identity (returns row to
  the bootstrap placeholder). One happy-path test per verb, one refusal (taken email → 409
  danger toast).

### C. Keys page (§4.19) — the agent-onboarding path

Verified against `ApiKeysGoldenPathBrowserTest`: it mints `endpoint` + `server` kinds only.

- **C1. MCP-key creation + the role-subset rule.** An author sees the MCP-kind card and a
  Role select offering exactly `author`; a workspace admin sees all three options and never
  `viewer`/`super admin`; mint succeeds and the row shows the member's role. This is the
  primary human→agent handoff flow; untested.
- **C2. Associations editor delta** — open the per-row disclosure, picker pre-checked,
  remove one path, save; the row's association cell updates; the service wrote the delta.
- **C3. Refusals** — name taken by a live key → `409 auth.key_name_taken` danger toast;
  bad custom expiry date → `400 auth.api_key.expiry_invalid` inline.
- **C4. Revocation authority matrix** — workspace admin sees a `server`-kind row with NO
  revoke verb (the row renders, the verb does not); an author's own MCP key revocable;
  expired key keeps its row and loses its verbs.
- **C5. "created by \<name\> (removed)"** — remove the member who created a key (pairs with
  H3); the key dies with them and the row says so.

### D. Executions (§4.8, §4.9)

- **D1. History filters actually filter.** `ExecutionHistoryBrowserTest` asserts the filter
  bar renders (verified: no test applies one). Seed ≥2 runs (one FAILED, one SUCCESS via
  `EditorRunFixtures`), select status=FAILED, assert the row set changes; pipeline dropdown
  narrows; the swap stays scoped to `#execution-table`.
- **D2. Execution detail — failed run.** Structured error record (code badge, message,
  correlation id, rendered SQL, exception chain), node stats with the error column, header
  FAILED badge. `PipelineEditorBoundariesBrowserTest` asserts canvas states on real runs but
  never the detail page of a failed run (verified).
- **D3. Execution detail — result panel states.** Success: preview table + pager + download
  links + effective expiry beside the title. No suite file downloads a result (verified) or
  asserts the expired / no-caller / failed cards:
  - **D3a. Downloads** — click each rendered download control, capture the browser's
    download event, and validate the suggested filename, format and decoded fixture data.
    Assert the response's `Content-Disposition` where captured. A direct in-page `fetch`
    may supplement the endpoint assertions but cannot prove the control works. Cover the
    detail page's JSON control here and the editor's JSON/CSV/Arrow controls in E2; reconcile
    any spec expectation for additional detail-page formats before dispatch.
  - **D3b. TTL expiry** — boot with a tiny result TTL (`@DynamicPropertySource`, the
    `PipelineEditorLeaseWaitBrowserTest` precedent) or rewind the row; the panel shows
    "Result expired — re-run", downloads hidden, stats/errors remain, Re-run works.
  - **D3c. No-caller state** — a write-back-only pipeline → "produced no caller result".
- **D4. Cancel from the detail page** — Cancel visible while RUNNING (shape-A toast +
  badge swap), then absent; a second cancel is answered 409 `pipeline.execution.not_running`
  and stays quiet. Editor-side cancel is covered; the detail-page button is not (verified).

### E. Pipeline editor — execute with parameters (§4.4, PE §7)

- **E1. Parameter form + strict wire-type coercion.** The editor execute fixtures in
  `EditorRunFixtures` are parameterless; `ScheduleFixtures` already declares INTEGER/DATE
  parameters for the schedule tests. The gap here is the editor's form and execute wire.
  Execute a pipeline declaring an INTEGER, a BIGINTEGER, a BOOLEAN and a DATE:
  INTEGER binds as a JSON number,
  BIGINTEGER stays a string, unparseable input marks the field `aria-invalid` and the POST
  never leaves the browser. This is the execute golden path's main branch.
- **E2. Results dock: paging, download, expiry.** First page is covered on real runs;
  cursor paging (prev/next, total), the download trio, and the TTL countdown → expired
  panel → Re-run are not (same verification as D3). Download acceptance uses the actual
  controls and browser download events, as specified in D3a.

### F. Datasources (§4.5)

- **F1. Connection test FAILURE path.** Register an unreachable datasource, Test → failed
  toast, Last-test badge flips to `failed` with the driver message on `title`; the row
  never says blank. Only the success toast is asserted (verified).
- **F2. The grants dialog (§4.5a).** `DatasourceGrantsPartialController` serves
  `GET/POST /partials/datasources/{name}/grants` and the remove route; the partial exists;
  **no browser test opens it** (verified: `DatasourcesGoldenPathBrowserTest:376` grants via
  in-page REST fetch, commenting "There is no grants SCREEN yet" — the dialog superseded
  that comment). Cover: super admin opens Grants → registering workspace badged; grant a
  second workspace → row + re-grant no longer offered; Revoke → row gone; a member gets no
  Grants verb (already asserted) AND the dialog route answers them with the role refusal.
- **F3. Register refusals** — duplicate name, missing required fields, unknown dialect:
  inline field errors, modal stays open (the modal-scoped-error rule). Only the
  out-of-range pool value is covered.

### G. Templates (§4.6, §4.7)

- **G1. Create-modal validation.** Only the success path is covered (verified). Blank name,
  grammar violation rendered from the server's own pattern, `sql` without a dialect,
  `javascript` refused `transform.js.unavailable` at save — each lands as the inline
  `[pane] code — message`, modal open, nothing written.
- **G2. Edit → draft → contextual Preview round.** Basic Preview is already covered:
  `ViewerAccessBrowserTest` clicks it as an author and checks SQL in `#previewPane` (see the
  method table). Remaining work: open a released template → Edit creates a draft
  copy-on-write (textarea editable, version badge `draft`); supply context → assert the
  rendered SQL uses that value; cause a render failure → assert it renders inline.
  `TemplatesGoldenPathBrowserTest` stops at create + select. Use the rendered controls as
  acceptance targets; reconcile §4.7's `#preview-output` wording with the implementation
  before freezing selectors.

## P1 — the role/permission matrix as a person meets it

The server-side matrix has `RoleWalkE2eTest`; the *rendered* ladder has
`RoleVisibilityBrowserTest`/`ViewerAccessBrowserTest`. What is missing is the second-order
rendering rules the spec is loudest about.

- **H1.** Admin verbs per role — a workspace admin gets no `/admin/users` (covered); a
  *super admin's* row verbs exist and a plain member's do not (B1/B2 build this).
- **H2. Lens 404 rule** — a promoter (and a viewer of a hidden object) opening a hidden
  pipeline/template URL gets the **not-found page**, never 403; a visible object's pending
  draft is invisible in version lists. `ViewerAccessBrowserTest` asserts 403s on
  `/promotion` and `/workspaces` but no lens-404 anywhere (verified).
- **H3. Workspaces member verbs** (§4.13) — own row renders no Save/Revoke/Remove (#208)
  and the server refuses with `409 workspace.self_membership`; Revoke-key renders only when
  a live key exists (#200); pending invitations are ghost rows with Revoke; a super admin's
  member row reads "super admin" with no dropdown. The row dropdown's happy path is covered;
  these four render-rule cases are not (verified against `RoleVisibilityBrowserTest`).
- **H4. The no-workspace page** (`workspaces/none`) — a member whose only workspace is
  deactivated lands on the explanatory page (not an error page), empty states elsewhere,
  no switcher. Only the super-admin-implicit-context arm is covered (verified).
- **H5. Search palette role scoping** — `HeaderSearchBrowserTest` is admin-only (verified).
  A promoter's palette shows lens-admitted pipelines and NO executions group; a viewer's
  hits open only what a viewer may open; blank query fetches nothing.
- **H6. Dashboard per role** — promoter: no Recent-executions panel, stat tiles count OWN
  runs (the #293 regression — tiles read zero — has no browser regression test); author:
  panel present, scheduled run visible with the `SCHEDULE` origin badge.
- **H7. Explorer Runs tab under R3** — same visibility as §4.8, rendered inside the detail
  pane (viewer sees own + scheduled; promoter own only). The tab's load-once is covered;
  its row-level visibility is not.
- **H8. Schedule verbs, role + state** — covered broadly (`SchedulesDetailBrowserTest`),
  including an explicit assertion that a blocked schedule hides Run now. Remaining gap:
  **Run now on a paused schedule succeeds** ("a person asked for it").

## P2 — refusal, state and edge paths

- **I1. Promotion failure states (§4.17).** With the stub-target idiom
  `PromotionSetsBrowserTest` already uses: target accepts → success flash with counts;
  target 500s → `target_unreachable` rendered IN PLACE on the listing (not a generic error
  page); `nothing_selected` when both lists arrive empty. The real two-deployment push
  stays in the integration suite (see NOT-list).
- **I2. API console with a real endpoint (§4.18).** Publish an endpoint (REST), bind a key:
  the row shows path, pipeline, the RELEASED version, method GET, key NAMES, Manage link;
  then discard the release → "no released version" state.
- **I3. Editor error surfaces (PE §9/§10).** On a failing run: Errors tab lists one entry
  per failed node (correlation id, rendered SQL, copy button); the failure modal is a
  one-line `alertdialog`, Esc closes; terminal `pipeline_failed` toast/modal exactly once
  across a history-restore (the `editor-toast-once` contract, browser-side).
- **I4. Editor connection lost (PE §15.1).** Abort the SSE from Playwright (`route.abort`)
  → banner; the two status polls then resolve the panel (abort/success/fail). Needs a short
  grace config via `@DynamicPropertySource`; the "closing the tab cancels the run" half can
  close the context and assert the execution ABORTED at the API.
- **I5. Theme persistence through Settings (§4.11).** Pick a palette in `/settings`' select
  → `users.theme_preference` row updated (assert via DB, the suite's established idiom),
  `#theme-link` swapped without reload, survives a fresh context. The shell toggle is
  covered; the Settings/menu swatches write the same field and are not.
- **I6. Error pages (§6).** `/error?status=403|404|500` render (500 with a correlation id),
  signed-in chrome; a bogus deep link 404s.
- **I7. Checks pane "Run checks" (§4.3b).** The release-dialog path is covered; the detail
  pane's Checks section with its own Run checks button (execute floor, `via=ui` row) is not.
- **I8. Keyboard tree walk (§4.6's contract).** ↑/↓ move selection with detail following,
  →/← expand/collapse, Enter opens the editor, `aria-selected` truthful. The indent/menu
  geometry is covered; the keyboard layer is not (verified).

- **MCP protocol behaviour, engine/DAG semantics, scheduler cron math (DST)** — unit +

- **Multi-browser matrix, visual pixel-diff, Lighthouse runs** — out of scope since the

- **Screenshot-only additions** — the suite already carries enough shots-only specs; every
  new test above asserts behaviour first.

## Testing strategy — the hands-off release (proposed, 2026-09-29)

Owner goal: **no manual use-case testing before a release, ever** — a solo-preneur budget
makes release-day clicking the most expensive test suite in the building. The audit above
is one of three holes; this section states the whole machine so review can ratify the
strategy and the tiers together.

**The principle: automation supplies evidence for integration and deployment separately.**
The proposed sequence preserves the repository's existing issue-completion policy:

```
merge to target branch → green local gate.sh on the merge SHA → push → green CI
→ record integration validation; close completed work and mark Done

owner authorizes deployment of a named revision → deploy → HTTP + browser smoke
→ record deployment acceptance separately
```

Unfinished acceptance remains tracked in GitHub; integration alone does not satisfy an
issue whose acceptance explicitly requires a deployed check. This proposal does not move
all issue closure to deployment or authorize automatic production deployments.

The local and CI layers below exist, but their cadence differs. Security mutations run
weekly or on demand, not on every push. Automation removes routine clicking; the security
pass on auth-touching diffs (working agreements, adopted 2026-09-21), review decisions and
operator responsibilities remain.

### Layer-by-layer inventory (source review; not a fresh execution verdict)

| Layer | What runs today | Verdict |
|---|---|---|
| Domain units | house-style JUnit 5 + MockK, Kover floors per module (module-structure §7.7) | retain; presence is not proof of complete behavior coverage |
| Persistence | Testcontainers integration tests; TEST-GAP Layer 3 records its earlier repository inventory as complete | retain; that historical inventory does not establish current completeness |
| Controllers/Web | plain-JUnit controller tests + Konsist/architecture guards (`ArchitectureGuardTest`, `RoleVisibilityRenderTest`) | retain |
| REST / full boot | CI `integration` job — the integration module + fat-jar smoke | retain |
| Contracts / docs | `docs-audit.sh` + spec-drift tests check their declared contracts; docs are build inputs | retain; prose and behavior outside those assertions can still drift |
| JavaScript | Gradle's `editorJsTest` (node --test), browser suite as backstop | retain |
| Security on CI pushes/PRs | `cold-verify` job, image-pin check and vulnerability scan; local gate also scans | retain; record results for the candidate revision |
| Periodic security assurance | separate `security-mutations.yml`: ten curated mutations, Mondays 04:17 UTC or manual dispatch; runner demands red then green and checks itself | retain; a green push does not imply mutations ran on that revision; extend for new security surfaces |
| Browser UI | 63 test classes in the browser module, whose `test` runs inside `build` and CI's gate job | review and close P0–P3; source count includes non-browser helper tests |
| Deployed environment | readiness/health probes and deployment procedures exist; no combined HTTP + browser smoke as proposed below | add artifact identity and deployed-origin journey evidence |

### The three holes, ranked

**1. The UI P0s (this document, tier P0).** Browser-specific failures in logout, admin-user
creation, MCP-key minting or result download can escape lower-layer tests. For example,
logout's relative redirect is guarded by an integration test, but that does not prove the
avatar-menu action and the resulting browser page work. These are gaps in journey evidence,
not claims that no mechanical guard exists at any layer.

**2. The post-deploy smoke.** The reverse proxy and HTTPS origin are part of the environment.
The #207 fix already has a repository guard: `LocalLoginE2eTest` asserts relative logout and
workspace-switch redirects. What remains unproven locally is browser behavior through the
deployed edge. Proposal: `scripts/smoke.sh <url> <expected-commit>`, coordinating HTTP probes
and a small Playwright journey after an owner-authorized deployment. Any later CI deployment
trigger is a separate decision.

HTTP acceptance:

- `/info` reports the expected commit supplied by the deployment record. `/health`'s version
  alone cannot identify an artifact: the baseline uses the shared version `0.0.1rc`. If a
  deployment intentionally omits the public commit, require a trusted deployment manifest
  linking the running image digest to that commit; missing identity evidence is a failure.
- `/ready` returns 200 and `/health` reports UP for every declared component.
- Local-login, logout and workspace-switch app redirects carry the expected **relative**
  `Location` values (deployment §6.2, #207). Resolve them against the public origin and
  require the expected same-origin HTTPS destination. Do not demand an absolute HTTPS header
  or introduce forwarded-protocol handling as a prerequisite for the shipped redirect fix.
- Assert the specified CSP directives and session-cookie attribute **values**, including
  the deployed Secure/HttpOnly/SameSite/path policy; mere header presence does not pass.
- `/docs` and one marketing route answer 200; an authenticated API probe with a dedicated
  key returns the expected payload as well as 200.

Browser acceptance through that same HTTPS origin:

- Sign in with a dedicated smoke account; verify the browser accepted its cookie and the
  authenticated dashboard renders.
- Switch between two controlled smoke workspaces; verify the final URL, active-workspace
  label and a workspace-specific fixture, so a server-side change with a stale page fails.
- Execute a bounded fixture pipeline in the editor; observe streamed progress and the
  terminal result through the edge, with expected fixture values.
- Log out using the avatar menu; verify the login page, absence of the session cookie and
  refusal of a subsequent protected navigation, including Back followed by a protected
  action. Collect CSP violations and unexpected console/network failures during the journey.

The implementation brief must define smoke-account/key provisioning, isolated fixture
ownership, cleanup and retained failure evidence. Record the expected and observed artifact,
target origin, per-check outcomes and an overall nonzero exit on failure. A failed smoke
leaves deployment acceptance open and invokes the existing deployment/rollback procedure;
it does not close acceptance work. Estimate effort after specifying this runner; the earlier
50-line HTTP-only estimate did not include the required browser evidence.

**3. Trustworthiness rules — green must mean green.** Automation is only hands-off if a
verdict never needs second-guessing:

- **No auto-retries, ever.** A flaky test is a lying test: file it, fix the same week
  (synchronise on events, never sleeps — the T263 coverage-floor lesson).
- **Every new test is falsified once** (revert the fix, watch it go red) before it counts —
  already house practice; make it a lane-prompt rule.
- **CI parity:** preserve the pinned class order and verify the same required test surface
  at the gate's and CI's configured fork counts. A pass at one fork count does not prove the
  other; record the configuration with the execution evidence.
- **Cold-cache for anything dependency-touching** — the recipe DEVELOPMENT.md records after
  the jackson incident; keep applying it.
- **Gate duration is a budget, not a target.** If the browser suite's growth makes
  `gate.sh` too slow, measure costs before proposing a nightly tier. `siteShots` is already
  outside `build`/`check`; moving behavioral tests out would change the per-commit guarantee
  and needs an explicit decision about which checks still gate release.

### The release ritual once all three land

Merge lane → `./scripts/gate.sh` → push → CI green → record validation and target-branch
integration in GitHub; close completed issues and mark their project items Done. Keep any
unfinished acceptance explicitly tracked. Deployment follows the owner's authorization of
a named revision, then `./scripts/smoke.sh https://… <expected-commit>` supplies a separate
deployment-acceptance record. Periodic security mutations retain their own revision/result
record. This establishes evidence for the enumerated contracts, not a guarantee against
every possible regression.

### Strategy-level NOT-list (complements the browser-scope NOT-list above)

- **No contract-testing framework (Pact etc.)** — the spec-drift test family already
  enforces code↔docs↔REST the idiomatic way for this repo.
- **No standing second staging environment proposed here** — the integration module provides
  isolated application tests but does not reproduce the deployed edge. The smoke covers that
  boundary; an ephemeral proxy-backed pre-deploy test remains an option for review.
- **No 100%-coverage targets** — floors plus security mutations detect more than a number.
- **No auto-retry in any suite, no screenshot-only browser specs** — the browser-scope
  NOT-list's rule, promoted to strategy.
