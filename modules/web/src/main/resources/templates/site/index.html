The agent loop

How it works

Agents are first-class principals here — not a plugin bolted onto a human UI. Your agent gets its own scoped credentials, its own protocol surface, and errors it can parse without scraping stack traces.

  1. Mint an API key

    Create it in the UI or with POST /api/v1/auth/api-keys.

    Keys are shown once, stored Argon2id-hashed, carry hierarchical scopes (read, execute, author, admin) and are pinned to one workspace.

  2. Point the agent at /mcp

    The MCP endpoint authenticates API keys only — DP-API-Key header or Bearer dpk_…. No cookies, no session roulette.

    Exactly 22 tools cover the full lifecycle: introspect datasources, author templates and pipelines, execute, inspect.

  3. Author as a JSON contract

    The agent creates a SQL template and a pipeline as declarative JSON — nodes, dependencies, parameters. Diffs review like code, because they are.

  4. Execute and watch

    Execution streams per-milestone events over SSE, with heartbeats, so the agent knows where things stand.

  5. Read row-level results

    executions_get_result returns the actual rows. The agent verifies its own work instead of asserting success.

This isn't a toy loop: the published demo set is ~4.9M sampled NYC taxi rows across Postgres, MySQL and SQLite — an agent authors and runs against exactly that.

Shipped, not promised

What's in the box

Each card cites the spec section it comes from — view source and spot-check us. Caveats included where they exist — honesty is the brand.

Author

Versioned JSON contracts

Pipelines are declarative JSON — schema_version, nodes, depends_on, parameters, settings. Every update mints a new immutable integer version, and the contract is additive-only.

Freemarker SQL templates

A save-time scan walks the parsed template AST against a forbidden-construct list — ?eval, ?new, ?api, in-body imports — so SSTI vectors are rejected before a template is ever saved. Library templates import declaratively.

Declared parameters bind as :name on a prepared statement — never interpolated. A template that interpolates a declared parameter into the SQL text instead is refused at save with template.validation.parameter_interpolated, and the message names the bind form to write.

Template versions, pinned by hash

Every template version is immutable — body, imports, dialect and engine are frozen once stored, versions are never reused or renumbered, and each carries a content hash. Pipelines pin {name, version}, so a new template version is invisible to them until an author moves the pin.

Templates are typed: sql (dialect required) or html (dialect absent, auto-escaping on). The type is fixed at creation and a database constraint enforces the pair.

Template hierarchy & explorer

A template's name is its path — acme/finance/monthly_revenue, up to ten segments. Folders are virtual: derived from name prefixes, with no identity, no CRUD and no rename, because a name is an identity every pin depends on.

The explorer is a real tree — one server-side prefix query per level, versions on the right, browse and search as two different presentations.

Draft → release → discard

One draft per entity, at most. Releasing locks the version: we never modify a released pipeline — the next change copies it into a new draft. Discard drops the draft and returns the number to the pool.

The editor's version select is read-only for anything but the working version, and Edit reuses the existing draft or copies the selected version into a new one — the rule is visible on screen, not just enforced behind it.

Used-by: impact before you change

The reverse arrow, answered as two different questions. Who uses this version now? scans every pipeline's working version and names the pipeline, the node id and the version carrying the pin — a fact you can go and change, not a count.

Is it safe to delete? scans every version ever, because historical versions stay executable. Delete is refused with 409 template.in_use while any pipeline version pins it.

Run

Seven SQL dialects

PostgreSQL, MySQL, SQL Server, Oracle, DuckDB, SQLite and H2 — one contract, seven engines.

Oracle and MySQL drivers are opt-in for license reasons (-Poracle/-Pmysql, or drop the jar in lib/); a missing driver fails at save with datasource.driver_not_loaded.

Cross-engine staging joins

Each execution gets its own isolated in-memory H2 tempdb — created at start, destroyed at end. Nodes stage ResultSets there, so downstream nodes join across engines.

Pipeline composition

A PIPELINE node executes a version-pinned child pipeline as a linked child execution — in-process, with lineage and family cancellation. The child keeps its own execution record, tempdb, stats and stream.

Pipeline graph view

The DAG renders as node cards, with the facts inside the box: name, a type badge, datasource · dialect, template @ version, and — after a run — elapsed time and rows. Colour carries state, the badge carries type, the ring carries selection.

It executes, streams, cancels, pages results and switches versions. What it deliberately does not do is author: there is no edit mode in v1, because authoring is agent-first.

Failures you can actually read

A failed node carries the catalogued code, the message, the node's own facts (datasource, dialect, template @ version), the rendered SQL in :name form — never a bound value — and the original exception chain with frames, root cause last.

The same record, built once, reaches the node_failed SSE event, the stored error_json, the editor's error surface and the agent's executions_get. No surface strips what another shows.

Live execution streams

POST /api/v1/pipelines/{id}/execute returns text/event-stream with per-milestone events and heartbeats. No stream resumption — a dropped connection cancels the execution rather than orphaning it.

Operate

Promotion between environments

Push dev → staging → prod from the UI. The screen lists only released versions newer than the target's; drafts never leave the authoring environment, and a same-version push is refused as a bug rather than swallowed as a no-op. Templates and child pipelines travel first, as a dependency closure.

The credential is a pre-shared server key, not a principal — no user account, so rotation and offboarding are independent. Absent key means promotion is refused; the receiver validates and never calls back.

Imported rows are stamped with a system service account that cannot log in, and the receiver's audit event records the source environment and a fingerprint of the key — never the key.

Multi-instance ready

Instances are symmetric and stateless for API, MCP, UI and auth — no sticky sessions. Only a running execution is pinned to one JVM; cancel works from any instance through Redis, and results, history and the event log are readable from all of them.

Datasource pool invalidation rides a Redis channel: repoint or rotate a credential on one instance and every other evicts its pool and rebuilds from the row, instead of serving stale credentials until restart.

A crashed instance's in-flight executions are swept to ABORTED by an idempotent stale-execution sweep every replica runs.

Append-only audit log

Logins, key lifecycle, scope denials, user admin, workspace events, promotion accept/reject, every MCP tool call and each credential-decryption point — recorded with actor, cause and source IP.

Catalogued error contract

Failures arrive as stable {domain}.{entity}.{failure} codes in a uniform error envelope — a catalog enforced against the code by drift tests, and the same codes over MCP. Agents get errors they can branch on, not prose to parse.

Govern

Workspaces & team isolation

Every request resolves exactly one workspace; all authored content is workspace-scoped; API keys are pinned to one workspace; roles are owner and member.

The management UI ships: create, switch, manage members, a navbar switcher and add-by-email.

OIDC SSO + scoped agent keys

Humans sign in through OIDC SSO. Agents get their own API keys with hierarchical scopes — separate principals, separate blast radii.

Local password accounts

No identity provider? Turn on local accounts and the whole product runs with zero external setup. Hashes are Argon2id through the same hasher API keys use; there is no self-registration — an admin creates the account, or config seeds the first admin only.

Every seeded or admin-reset credential is one-time and the app refuses every other screen until it is changed. Unknown email, OIDC-only account and wrong password give the same banner, the same status and the same cost — the no-row path still runs one Argon2 verification, so timing cannot enumerate. Five consecutive failures lock the account without spending any more hashing memory.

Read-only datasource governance

is_readonly forbids write-shaped uses — enforced at save time, at an executor backstop, and as Hikari readOnly. Admin-gated on globals. The flag is a contract, not containment: pair it with a SELECT-only DB user.

Encrypted datasource credentials

Passwords are AES-256-GCM encrypted with the row's name bound as additional authenticated data, so a ciphertext moved between rows fails to decrypt. The app refuses to start without a valid key.

Every credential carries a key version and datapipelines.db.key-provider selects where the key comes from — one contract test every provider passes.

The demo is the quickstart

Real NYC data, one command

./app.sh --start --demo-nyc builds the jar, downloads the published mobility/v2 sample set, verifies every checksum before touching an engine, restores three databases, creates a SELECT-only demo login, registers three global read-only datasources, and seeds 17 templates and six example pipelines into your workspace at first login.

  • PostgreSQL — ~4.9M hash-sampled TLC yellow-taxi rows, plus rollups.
  • MySQL — NOAA GHCN-Daily weather for 5 NYC stations.
  • SQLite — a reference database.
  • Deterministic build — every source URL and SHA-256 pinned; hash-based sampling, never random.
  • Checksummed manifest — with provenance recorded per source, behind a pre-publication license gate.
  • Six worked pipelines — up to five nodes, three engines in one run, a composed child pipeline, and a shared template library. Each one has a recorded expected result, checked by check-baselines.sh.

Same command, same bytes, same rows — every time. Your agent gets a reproducible sandbox with something real to chew on.

A second family ships beside it. --demo-trade adds US Census monthly imports and exports at HS-6 grain on DuckDB — the demo's fourth engine — UN Comtrade mirror statistics on MySQL, and Federal Reserve H.10 exchange rates on SQLite, with three more example pipelines that reconcile what the United States reports against what its partners report. This product uses the Census Bureau Data API but is not endorsed or certified by the Census Bureau.

Your infra, your rules

Security & self-hosting

Runs on your hardware, under your policies. The defaults are paranoid so you don't have to be.

  • Authenticated by default. Every endpoint requires auth unless it's explicitly allowlisted.
  • Encrypted credentials. Datasource passwords are AES-256-GCM encrypted with the row name bound as AAD — and the app refuses to start without a valid key.
  • Least privilege as the documented pattern. The demo provisions a SELECT-only database login; the same pattern is documented for your own datasources.
  • TLS is your job. Terminate TLS at your own proxy — we don't pretend a built-in would fit every network.

What's next

Roadmap

Planned work — no dates promised. Everything here is explicitly future-tense; the rest of this page describes what ships today, caveats attached.

Coming soon

Result visualization & dashboards

Charts and dashboards over pipeline results, in-product.

  • Pipeline and template editing in the UI

    Create, edit and save from the browser. Today both editors display, preview, release and execute; authoring goes through MCP and the REST API. When it lands it rides the existing draft lifecycle — a released version is never the edit target.

  • DuckDB as a staging engine

    settings.tempdb.engine: "DUCKDB" for large analytical joins. DuckDB already ships as a dialect and, since the trade demo family, as a sample-data engine; backing the staging tempdb with it is what remains.

  • Auto-created write-back tables

    output.auto_create: true emits a CREATE TABLE IF NOT EXISTS from the ResultSet's own metadata, so writing a result back no longer needs a DDL node in front of it.

  • A shipped KMS key provider

    The contract half already ships: credentials carry a key version, datapipelines.db.key-provider selects the source, and one contract test every implementation passes. What is left is a vendor implementation — a written procedure, not a design.
