Run it, then build on it

How it works: the MCP server tutorial, end to end on your laptop

Eight steps, each executed on a fresh checkout before it was written here. Start the server with sample data. Copy your MCP key from the top bar. Connect Claude Code, Cursor or Copilot over MCP. Let the agent author and run a pipeline, release it, publish it as an API, scope a key to that API, and call it. Every command, config block and response below is copied from that run.

Start at step 1 → Skip to the engineering depth

Step 1

Run it locally, with sample data

You need Docker with the compose plugin and a checkout of the repository. Nothing else. The build runs inside a throwaway JDK container, so there is no local Java to install. One command:

./app.sh --start --demo nyc,trade,lake

What you see. The first build is the slow one because the dependency cache is cold. Later starts reuse it. When the stack is healthy the script prints the address and the login it seeded:

==> UP — http://localhost:8080
==> LOGIN: admin@local.test / <a generated one-time password>
    The one-time credential from deploy/secrets.env is still pending — the app will make
    you set a new password at first sign-in (auth.md §5A.4).
==> demo data loaded (nyc,trade,lake). The example pipelines are seeded into the
    shipped 'demo' workspace — the one every login lands in (auth.md §4.2 step 4).

What just happened. The script started Postgres, Redis, the app and the demo loaders, ran the migrations and seeded the first admin behind a one-time password. The --demo flag restored three published sample families and registered them as read-only datasources with example pipelines beside them: NYC taxi trips on Postgres, NOAA weather on MySQL, the zone reference on SQLite, US trade at HS-6 grain on DuckDB, and a rideshare lake read in place as Parquet and Iceberg on S3.

Now open http://localhost:8080 and sign in with the printed login. The app forces a password change of twelve characters or more before anything else, then lands on the dashboard. You are already inside the demo workspace, which is where the example pipelines live.

Step 2

Copy your MCP key from the top bar

What you do. Sign in. That is all it takes to get a key: your MCP key is created for you and waits in the top bar, on the right, as the dpk_… chip beside your account menu. Copy puts the full key on your clipboard; paste it into the client config in step 3.

What you see. You get exactly one key per workspace per person. The demo login's role is admin, so its reach is read, execute and author. That is the whole ladder an authoring agent needs. A viewer's key would carry read and execute. The role decides, never a form.

What just happened. The key was created when you signed in and pinned to the workspace you entered, demo here. It is sealed at rest so the top bar can open it for a copy. There is no endpoint that creates one, on purpose: GET /api/v1/auth/api-keys/mine reads it, and rotating it means deleting it with the chip's button and signing in again. Administration stays with signed-in people; no key can hold it.

Step 3

Point the agent at /mcp

What you do. Every client needs the same two facts: the endpoint POST http://localhost:8080/mcp and the key from step 2 in the DP-API-Key header. The blocks below are the ones the setup page shows. They are one shared fragment, so the two pages cannot drift.

What you see, from Claude Code on the run this page was written from:

$ claude mcp list
…
datapipelines: http://localhost:8080/mcp (HTTP) - ✔ Connected

What just happened. The client ran the MCP initialize handshake against /mcp with the key, and the server answered with its capabilities and its working instructions: the authoring flow, the naming rules, and what it may not do. The endpoint accepts API keys only; a browser session is refused, deliberately. Exactly 30 tools cover the full lifecycle, starting with pipelines_list and datasources_list.

Step 4

The agent authors a pipeline and runs it

What you do. Ask a question in plain language. This is the prompt the run used, verbatim:

List the datasources and their schemas to find the NYC taxi trips and the daily
weather. Author a NEW pipeline under the test/ folder that answers: total fare
revenue per NYC borough, split by rainy vs dry days. It must join the trips data
with the weather data. Execute it and read the result rows. Do not release
anything. Stop after reporting.

What you see. The agent works the server's own authoring flow, in this order. The calls below are from the run's transcript:

  1. pipelines_list and datasources_list: the existing folders and the demo datasources.
  2. datasources_get_schemas → get_tables → get_columns: the real columns, read, never recalled.
  3. sql_probe: candidate SQL against each source, before anything exists.
  4. templates_create and templates_render: the SQL previewed before a pipeline references it.
  5. pipelines_create: test/borough_fare_by_weather, a versioned JSON DAG of SQL nodes.
  6. pipelines_execute → executions_get_result: SUCCESS, 12 rows in under four seconds.
  7. pipelines_run_checks: the release checks pass.

The first rows of the answer, on 2024 defaults. The est ×16 column scales the 1-in-16 sample to the population:

Fare revenue per borough, rainy vs dry days. The pipeline's first rows.
BoroughWeatherDaysTripsFare, sampledFare, est ×16
Manhattandry2901,741,947$28,048,896.60$448,782,345.60
Manhattanrainy76462,115$7,465,129.64$119,442,074.24
Brooklyndry29027,697$776,411.11$12,422,577.76
Brooklynrainy767,171$200,777.83$3,212,445.28

What just happened. Each node read its own engine: trips from Postgres, rainfall from MySQL, the borough lookup from SQLite. The federated join happened in a per-run in-memory staging database that exists only for the execution. Nothing was copied into a warehouse first. And the agent stopped at draft, because no MCP tool can release anything. That is a design rule, not a demo limitation.

Step 5

A person releases it

What you do. Open the pipeline in the editor and choose Release v1…. This is the step the agent cannot do for you. Release needs the promote role, which the bootstrap admin from step 1 holds, and there is deliberately no MCP tool for it.

What you see. The dialog runs the pipeline's release checks as it opens and answers every template pin before it offers the button. The two draft templates the agent created ride along through the checked consent. One click, and the response flips the pipeline to RELEASED.

What just happened. Version 1 became immutable. Everything that serves the pipeline now runs the released logic: the executions, and the endpoint you are about to publish. A further change is a new draft that changes nothing live. The same release exists as POST /api/v1/pipelines/{id}/release.

Step 6

Publish it as an API

What you do. One POST, from a shell, or the endpoints_create MCP tool if the agent is doing it:

curl -X POST http://localhost:8080/api/v1/endpoints \
  -H "DP-API-Key: dpk_<id>.<secret>" -H "Content-Type: application/json" \
  -d '{"path": "/nyc/v1/borough-fare-by-weather",
       "pipeline": "test/borough_fare_by_weather",
       "description": "Fare revenue per borough, rainy vs dry days"}'

What you see. 201, with the URL the path grammar built:

{"schema_version": 1, "data": {
  "path": "/nyc/v1/borough-fare-by-weather",
  "pipeline": "test/borough_fare_by_weather",
  "enabled": true,
  "url": "/api/nyc/v1/borough-fare-by-weather", …}}

What just happened. Publication is refused unless the pipeline has a released version and is side-effect-free. Every node reads, and writes at most to the per-run tempdb or to the caller. That is what makes a GET safe to retry, preload or crawl. The path is category, version, path, and a category like v1 or the literal api can never be published, so a published path can never shadow a product route. The API section in the UI lists the endpoint; managing it stays on REST and MCP.

Step 7

Scope an API key to the endpoint

What you do. An admin creates an API key on the API keys page at /api-keys and associates it with the endpoint's path. In the demo you are the admin, so this is you. Pick the kind API key, which is the endpoint kind on the wire, add a name, and set the path under Associated endpoints. Or do it over REST:

curl -X POST http://localhost:8080/api/v1/auth/api-keys \
  -H "DP-API-Key: dpk_<id>.<secret>" -H "Content-Type: application/json" \
  -d '{"name": "weather-app", "kind": "endpoint",
       "bindings": ["/nyc/v1/borough-fare-by-weather"]}'

What just happened. An endpoint key carries no scopes at all. Its authority is exactly its bindings, and the nearest bound ancestor decides: a binding to /nyc would cover every endpoint under it. The negative control, from the same run: the agent's key from step 2, the one that authored the pipeline, is refused here:

$ curl http://localhost:8080/api/nyc/v1/borough-fare-by-weather \
    -H "DP-API-Key: dpk_<the agent key>"
403 — {"error": {"code": "endpoint.key_not_bound", …}}

Step 8

Call it, and page the result

What you do. A GET with the endpoint key. No session, no SDK:

curl http://localhost:8080/api/nyc/v1/borough-fare-by-weather \
  -H "DP-API-Key: dpk_<id>.<secret>"

What you see. 200, and the first page with its cursor. The output below is trimmed; the run returned 12 rows:

{
  "execution_id": "2e9236bd-707d-4f23-b71a-8757ad9ae64b",
  "schema": [{"name": "borough", "type": "STRING"}, …],
  "rows": [["Bronx", "dry", "290", "5718", 185793.34, …], …],
  "row_count": 12, "total_rows": 12, "has_more": false,
  "result_url": "http://localhost:8080/api/v1/executions/2e9236bd-…/result",
  "ttl_seconds": 300
}

What just happened. The endpoint executed the latest released version in-process, audited against the key, and materialized the full result before answering. DP-Result-Page-Rows: 5 returns five rows with has_more: true, and the cursor pages the rest inside the TTL with GET …/result?offset=5&limit=5. The pipeline's declared parameters arrive as the query string, like ?year=2023. Validation is strict on purpose: a typo like ?yr=2023 is a 400 listing every accepted parameter, because a silently defaulted year would return plausible, wrong rows. A run that outlives the endpoint's timeout answers 202 with the cursor instead of an error. The answer is coming.

The whole mechanism in one paragraph

A dataset here is a pipeline: a versioned JSON DAG of SQL nodes the agent authors over MCP against your real schemas. Each node runs on its own engine: Postgres, MySQL, SQL Server, Oracle, SQLite, DuckDB, or Parquet and Iceberg on S3 through dp-lake. Cross-engine joins happen in an in-memory staging database that exists only for the run. Nothing is copied to a warehouse; nothing lands. A release is immutable, and a released pipeline can be published as a GET endpoint.

Shipped, not promised

What's in the box

Each card cites the spec section it comes from. View source and spot-check us. Caveats included where they exist. Honesty is the brand.

Author

Versioned JSON contracts

Pipelines are declarative JSON: schema_version, nodes, depends_on, parameters, settings. Every update creates a new immutable integer version, and the contract is additive-only.

Freemarker SQL templates

A save-time scan walks the parsed template AST against a forbidden-construct list: ?eval, ?new, ?api, and in-body imports. SSTI vectors are rejected before a template is ever saved.

Declared parameters bind as :name on a prepared statement and are never interpolated. Interpolating one into the SQL text instead is refused at save with template.validation.parameter_interpolated.

Template versions, pinned by hash

Every template version is immutable. Body, imports, dialect and engine are frozen once stored, versions are never reused or renumbered, and each carries a content hash. Pipelines pin {name, version}, so a new template version is invisible to them until an author moves the pin.

Templates are typed: sql, which requires a dialect, or html, which has none and turns auto-escaping on. The type is fixed at creation and a database constraint enforces the pair.

Names are paths, and a folder is mandatory

A template's or pipeline's name is its path: nyc/mobility/revenue_by_borough, 2 to 10 segments. The first one is a folder, and the root holds folders only. A flat name is refused with details.reason = "folder_required".

An agent that invents a NEW top-level root is refused until it says so on purpose: confirm_new_root, with the roots that already exist in the error's details. Asking a person before creating a namespace is a guarantee here, not advice.

Draft → release → discard

One draft per entity, at most. Releasing locks the version: we never modify a released pipeline. The next change copies it into a new draft. Discard drops the draft and returns the number to the pool.

The editor's version select is read-only for anything but the working version, and Edit reuses the existing draft or copies the selected version into a new one. The rule is visible on screen, not just enforced behind it.

Used-by: impact before you change

The reverse arrow, answered as two different questions. Who uses this version now? scans every pipeline's working version and names the pipeline, the node id and the version carrying the pin. That is a fact you can go and change, not a count.

Is it safe to delete? scans every version ever, because historical versions stay executable. Delete is refused with 409 template.in_use while any pipeline version pins it.

Run

Eight engines, one contract

PostgreSQL, MySQL, SQL Server, Oracle, DuckDB, SQLite, H2, and LAKE, object storage read in place. One pipeline contract over all of them.

Oracle and MySQL drivers are opt-in for license reasons: pass -Poracle or -Pmysql, or drop the jar in lib/. A missing driver fails at save with datasource.driver_not_loaded. Everything else is in the published image, the DuckDB extensions included. A hardened deployment needs no egress to an extension repository.

dp-lake: Parquet and Iceberg, read in place

A LAKE datasource queries Parquet and Apache Iceberg on S3 or any S3-compatible store with no warehouse and no load step. DuckDB is the engine; the catalog is the server's own registry, dp-catalog. Tables are registered over REST or by an agent through the lake_tables_* tools.

Hive-partitioned Parquet is scanned with partition pruning, so a date predicate reads the days it names and not the table. It is a read connector: there is no write path to the bucket. The whole dp-lake story →

Cross-engine staging joins

Each execution gets its own isolated in-memory H2 tempdb, created at start and destroyed at end. Nodes stage ResultSets there, so downstream nodes join across engines.

Pipeline composition

A PIPELINE node executes a version-pinned child pipeline as a linked child execution, in-process, with lineage and family cancellation. The child keeps its own execution record, tempdb, stats and stream.

The pipeline editor

The DAG renders on a full-bleed canvas as node cards, with the facts inside the box: name, a type badge, datasource · dialect, template @ version, and after a run, elapsed time and rows.

One dock, four tabs: Details, Results, Errors and Events. A failure opens Errors, every event in arrival order.

It executes, streams, cancels and pages results. What it deliberately does not do is author: there is no edit mode in v1. Authoring is agent-first.

Failures you can actually read

A failed node carries the catalogued code, the message, and the node's own facts: datasource, dialect, template @ version. It carries the rendered SQL in :name form, never a bound value, and the original exception chain with frames, root cause last.

The same record, built once, reaches the node_failed SSE event, the stored error_json, the editor's Errors tab and the agent's executions_get. No screen strips what another shows.

Live execution streams, and a cancel that means it

POST /api/v1/pipelines/{id}/execute returns text/event-stream with per-milestone events and heartbeats. There is no stream resumption. A dropped connection cancels the execution rather than orphaning it.

Cancel reaches the executing instance through Redis from any instance, and a per-node latch refuses to enter the driver once it has fired. A cancelled execution cannot come back SUCCESS. The window where it could was closed, and a test covers it by injecting the descheduling rather than racing it.

Operate

Promotion between environments

Push dev → staging → prod from the UI. The screen lists only released versions newer than the target's; drafts never leave the authoring environment, and templates and child pipelines travel first, as a dependency closure.

The credential is a server-kind API key, not a principal. It has no user account, so rotation and offboarding are independent of any person. To rotate: create a second key, set it on the sender, revoke the first. Neither side restarts.

Read the spec →

Multi-instance ready

Instances are symmetric and stateless for API, MCP, UI and auth. There are no sticky sessions. Only a running execution is pinned to one JVM; cancel works from any instance through Redis, and results and history are readable from all of them.

Datasource pool invalidation rides a Redis channel: repoint or rotate a credential on one instance and every other evicts its pool and rebuilds from the row.

A crashed instance's in-flight executions are swept to ABORTED by an idempotent stale-execution sweep every replica runs.

One API section

Everything a program uses to talk to a workspace, on one screen: the endpoints you have published as GET /api/…, the keys that may call them, and the MCP connection block. The tool count is rendered live from the catalog, never a literal.

It is honest about what it cannot show. There is no "calls in the last 24 h" column: every serve is audited, but nothing tallies them per endpoint. The card states the absence instead of filling it from a sample.

Read the spec →

Connection pools you can see and set

Eight HikariCP settings are on the datasource form, each prefilled with its effective default and labelled with where that default came from. A field left alone is not persisted, so a later change to a product default still reaches the datasource.

Out-of-range values are refused, not accepted. Every floor restates a rewrite Hikari would otherwise perform silently, and the test that justifies them builds a real pool and watches it happen.

Read the spec →

A saved datasource never kills a running query

Editing or deleting a datasource retires its pool instead of closing it: new leases build a fresh pool from the new row at once, idle connections close now, and a connection still in use closes when its borrower returns it, never mid-statement.

Delete asks the question first: the dialog runs the any-version usage scan before it offers anything, and lists pipeline › node (v3 released) for every reference. The 409 and the dialog cannot disagree. It is the same scan.

Append-only audit log

Logins, key lifecycle, scope denials, user admin, workspace events, promotion accept/reject, every MCP tool call and each credential-decryption point, recorded with actor, cause and source IP.

Catalogued error contract

Failures arrive as stable {domain}.{entity}.{failure} codes in a uniform error envelope. It is a catalog enforced against the code by drift tests, and the same codes flow over MCP. Agents get errors they can branch on, not prose to parse.

Govern

Workspaces & team isolation

Every request resolves exactly one workspace; all authored content is workspace-scoped; API keys are pinned to one workspace. Membership comes in five roles: viewer, author, promoter, workspace admin and super admin.

The management UI ships: create, switch, manage members, a navbar switcher and add-by-email.

A key has a kind, and the kind decides its reach

Three kinds. A user key is an agent's key and a program's key. Its authority is its scopes. An endpoint key authorises the published paths it is bound to. A server key opens the promotion routes and nothing else.

The confinement is decided centrally, before any handler's annotation is read. A new route cannot become quietly reachable to a scopeless key.

Read the spec →

The agent never sees a credential

There is deliberately no tool that registers a datasource, and none that creates a key: a credential through a tool call would land in the agent's context and transcript. A person adds the datasource in the UI; the agent uses it by name.

What the agent keeps is everything that needs no secret: list, get, test, schemas, tables, columns and preview rows. Enough to author without a password.

Read the spec →

OIDC SSO + scoped agent keys

Humans sign in through OIDC SSO. Agents get their own API keys with hierarchical scopes. Separate principals, separate blast radii.

Local password accounts

No identity provider? Turn on local accounts and the whole product runs with zero external setup. Hashes are Argon2id through the same hasher API keys use. There is no self-registration: an admin creates the account, or config seeds the first admin only.

Every seeded or admin-reset credential is one-time and the app refuses every other screen until it is changed. Five consecutive failures lock the account. The unknown-email path spends the same hashing memory, so timing cannot enumerate it.

Read the spec →

Read-only datasource governance

is_readonly forbids write-shaped uses. It is enforced at save time, at an executor backstop, and as Hikari readOnly. Admins turn it on for global datasources. The flag is a contract, not containment. Pair it with a SELECT-only DB user.

Encrypted datasource credentials

Passwords are AES-256-GCM encrypted with the row's name bound as additional authenticated data, so a ciphertext moved between rows fails to decrypt. The app refuses to start without a valid key.

Every credential carries a key version, and datapipelines.db.key-provider selects where the key comes from. One contract test covers every provider.

Your infra, your rules

Security & self-hosting

Runs on your hardware, under your policies. The defaults are paranoid so you don't have to be.

  • Authenticated by default. Every endpoint requires auth unless it's explicitly allowlisted.
  • Two variables, two files. An org sets what it calls the environment with DATAPIPELINES_ENV, and how careful the product should be with DATAPIPELINES_POSTURE: development or hardened. Configuration lives in exactly two files. A tracked deploy/env/defaults.env carries every non-secret default. A git-ignored deploy/secrets.env holds the secrets, and ./app.sh --scaffold writes it for you with every secret generated. The hardened setting refuses the demo at boot.
  • The rate limiter fails closed. If Redis, where the counters live, is unreachable, requests are refused with 429 rate_limit.unavailable rather than waved through. A limiter that opens under its own outage is not a limit.
  • Encrypted credentials. Datasource passwords are AES-256-GCM encrypted with the row name bound as AAD. The app refuses to start without a valid key.
  • Least privilege as the documented pattern. The demo provisions a SELECT-only database login; the same pattern is documented for your own datasources.
  • No surprise egress. The DuckDB extensions dp-lake needs are baked into the published image and loaded from disk, so a hardened deployment never reaches out to an extension repository at runtime. What a lake query costs in bytes is bounded by the query's own predicates, and the docs say so before you turn it on.
  • TLS is your job. Terminate TLS at your own proxy. We don't pretend a built-in would fit every network.
