Parameter sets

Define inputs once. Reuse them in dashboards.

A parameter set is a versioned definition of the filters a person fills in: typed text and number inputs, dropdowns and multi-selects, their defaults, their validation and the choices that depend on other choices. The server evaluates the whole form, so every dashboard that pins the set gets the same rules.

The parameter sets API Where sets are used

What a set holds

Typed inputs and choices, one validator

INPUT: a value someone types

A date, an amount, a name. It has a type, an optional default and optional constraints such as a minimum or a pattern. A value that breaks a rule is refused, never rounded or trimmed: an amount with two decimal places will not accept a third.

SELECT: a value someone picks

One choice or several. Each option is a value, the label a person reads and whether it is the default. Options are written into the set for lists that rarely change, or read from your database by a pinned SQL template for lists that do.

{
  "name": "state",
  "label": "State",
  "type": "STRING",
  "kind": "SELECT",
  "cardinality": "SINGLE",
  "required": true,
  "source": { "template": { "id": "acme/sales/states_of_country.sql", "version": 3 },
              "datasource": "warehouse" },
  "depends_on": ["country"],
  "presentation": { "control": "dropdown" }
}

One parameter from the engine's own example set: the state list depends on the chosen country.

Cascading filters

Pick a country, get its states

  1. The selector is a reviewed SQL template

    The state list comes from a pinned template version, so the query behind a dropdown is reviewed and released like any other SQL. It returns a value, the text to show and the default flag, in a declared order.

  2. Parents bind as parameters

    The chosen country reaches the state query as a bound parameter, never pasted into the SQL text. A city list can depend on the state the same way, as long as the chain has no cycle.

  3. The server evaluates the whole form

    The client sends every control's current value; the server answers with fresh options, the resolved value of each control and any errors. A choice that no longer exists falls back to the default and says it was reset.

POST /api/v1/parameter-sets/{id}/evaluate
{ "version": 4,
  "selections": { "country": "USA", "state": "NY", "city": null, "min_order_amount": 250.00 } }

The evaluate request from the REST contract. A first render sends empty selections and gets the whole form back.

Versions and review

Versioned like a pipeline

Draft, release, switch

An agent creates or edits a set as a draft over the MCP tools. A person releases it, and can discard, restore or switch versions with the same lifecycle templates use.

Protected while pinned

A dashboard pins one exact set version. That version cannot be discarded or purged while it is pinned; the server names the dashboards that hold it.

A live form and a history

The Parameter Sets page renders the form and evaluates it as you change values, and its History tab lists every evaluation of the set: when, from which surface, by whom, its status and how long it took.

Current limits

What a parameter set is not

  • Not a pipeline's own parameters. A pipeline declares its typed parameters, and an API call or a schedule supplies values for them. A set maps its values onto those parameters through a dashboard.
  • Dashboards are the consumer today. A set does not attach to a published endpoint or a schedule.
  • Not schedule dates. TODAY and YESTERDAY on a schedule are bindings of the scheduler, separate from sets.
  • Not access control. A set shapes and validates choices. Which rows a viewer may see is decided where the viewer is authorized.
