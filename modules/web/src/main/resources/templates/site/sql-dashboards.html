SQL dashboards

Turn pipeline results into useful dashboards.

A dashboard here is built from the SQL pipelines you already review: charts, tables and KPI cards bound to pinned pipeline versions, with filters a viewer can change. It runs on your own server, an agent drafts it, a person releases it, and your product can show it to customers without the key ever reaching their browser.

The dashboards contract Customer-facing analytics

How it is built

A pipeline, a visualization, a dashboard

  1. A released pipeline is the source

    A dashboard pins exact pipeline versions as its sources. Every source must pass the read-only rule, checked at save, at release and again before each refresh, so a pipeline with a write node is never a source.

  2. A visualization is a reusable chart

    A Plotly chart, a table or a KPI card, bound to named inputs rather than to one pipeline. The same release can appear on several dashboards. Bar, line and scatter, pie, histogram, box and heatmap are supported, with three 3D trace types loaded only when a dashboard uses one.

  3. A dashboard arranges them

    It maps source results onto each visualization's inputs, places them on a 12-column grid, groups them, and adds parameter controls from one pinned parameter set and the refresh actions a viewer presses.

Review and run

Drafted by an agent, released by a person

Drafts first

An agent creates and edits visualizations and dashboards over MCP, and everything it writes is a draft. A person opens the draft in the application, checks it and releases it.

Tested before release

A visualization declares test cases, and it releases only with a passing run for its exact content plus the server's own mechanical check. A change after the run makes the evidence stale.

Released means pinned

A released dashboard requires released dependencies, and every reference is an exact version. Editing a chart opens a new draft; the board that pinned the old one keeps it.

A refresh you can watch

Opening a board or applying its filters runs its sources and streams each chart's result as it arrives. Two charts reading the same source and values share one run, and a viewer can abort a refresh.

A record of every refresh

Every admitted refresh is recorded and closed however it ends, with one audit row per refresh. Its source runs appear among the person's executions.

Bounded per refresh

Each source's rows are counted against a byte cap, a refresh reserves its execution slots all at once or waits, and a full instance answers with a retry time instead of queueing without limit.

Embedding

Show a dashboard in your product, keep the key on your server

Your backend holds a dashboard key and relays the four runtime routes: the configuration, the parameter evaluation, the refresh stream and the abort. The browser talks only to your backend: the proxy attaches the key server-side and strips cookies and CSRF headers. The source includes a dependency-free reference proxy and a test that fails if a proxy buffers the stream or forwards a cookie.

Your backend decides who your user is: the reference proxy is an example you place behind your own sign-in. Every viewer behind one key shares that key's identity and budget, so the key does not separate one customer's data from another's. If a viewer may only see their own rows, your backend checks the values it forwards, and the source pipeline filters on them.

Current limits

What dashboards do not do yet

  • Read-only is declared, not enforced by the database. A source is admitted by its nodes' declared types and targets; running source statements on a read-only connection is tracked separately.
  • No drag-and-drop editor. The layout is part of the dashboard document an agent writes and a person reviews.
  • Refreshes, not live feeds. A refresh streams progress while it runs; there are no continuous subscriptions, and a schedule does not refresh a dashboard.
  • No report delivery or alerts. Scheduled report mail, PDF export and condition alerts are not built.
  • The refresh history is not relayed. A shared key cannot tell your viewers apart, so the reference proxy leaves those routes out; build your own per-user history if you need one.
